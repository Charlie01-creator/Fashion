# API Reference

Base URL: `http://localhost:4000/api` (dev)

All responses follow:
```ts
{ success: true, data: T, message?: string }
// or
{ success: false, error: { code: string, message: string, details?: unknown } }
```

## Auth

### POST /auth/register
Body: `{ name: string, email: string, password: string (min 8 chars) }`
→ 201, `{ user, tokens: { accessToken } }`. Sets `refreshToken` httpOnly cookie.
Rate limited: 20 requests / 15 min / IP.

### POST /auth/login
Body: `{ email: string, password: string }`
→ 200, `{ user, tokens: { accessToken } }`. Sets `refreshToken` httpOnly cookie.
Rate limited: 20 requests / 15 min / IP.

### POST /auth/refresh
No body — reads `refreshToken` cookie. Rotates the refresh token.
→ 200, `{ user, tokens: { accessToken } }`.

### POST /auth/logout
No body — reads and revokes `refreshToken` cookie.
→ 200, `{ data: null }`.

## Users (protected — requires `Authorization: Bearer <accessToken>`)

### GET /users/me
→ 200, current user + profile.

### PATCH /users/me
Body (all optional): `{ name?, stylePreferences?: string[], favouriteColors?: string[] }`
→ 200, updated user + profile.

## Clothing (protected — requires `Authorization: Bearer <accessToken>`)

Every clothing endpoint is scoped to the authenticated user — items belonging to other users return 404, never 403, to avoid confirming an item's existence.

### POST /clothing/upload
`multipart/form-data`, field name `image` (JPEG/PNG/WebP, ≤5MB). Stores the image via the storage provider — does not create a ClothingItem record.
→ 201, `{ url, key }`. Rate limited: 60 requests / 15 min / IP.

### POST /clothing
Body: `{ imageUrl, imageKey, category, color, style?, season, tags? }` (imageUrl/imageKey from the upload step above). `aiMetadata` is never client-settable — sending it is rejected.
→ 201, the created item, with `aiStatus: "PENDING"`. AI analysis is queued and runs in the background — the response does not wait for it.

### GET /clothing
Query: `category?`, `page?` (default 1), `limit?` (default 24, max 50).
→ 200, `{ items, pagination: { page, limit, total, totalPages } }`.

### GET /clothing/:id
→ 200, the item, including `aiStatus`, `aiMetadata`, `aiErrorMessage`, `aiAnalyzedAt`.

### POST /clothing/:id/analyze
Re-runs AI analysis for one item (used for retry after a failure, or to refresh a completed one). Synchronous — the request waits for the result, since the user is looking at a "retry" button and expects to wait. Rate limited: 30 requests / 15 min / IP.
→ 200, the updated item.

### DELETE /clothing/:id
→ 200, `{ data: null }`. Also deletes the underlying stored file (best-effort — failure here doesn't fail the request, see docs/ARCHITECTURE.md).

`aiStatus` is one of `"PENDING" | "ANALYZING" | "COMPLETED" | "FAILED"`. `aiMetadata` is `null` until status is `"COMPLETED"`; when present it includes `category`, `color`, `style`, `pattern`, `material`, `seasonSuitability[]`, `occasionSuitability[]`, `tags[]`, `confidence`. `aiErrorMessage` is set only when status is `"FAILED"`.

## Outfits (protected — requires `Authorization: Bearer <accessToken>`)

Every outfit endpoint is scoped to the authenticated user — same 404-not-403 ownership pattern as clothing.

### POST /outfits/generate
Body: `{ occasion: "casual"|"formal"|"party"|"work"|"wedding", weather?: { temperatureC?, condition? } }`. Runs the recommendation engine against the user's own wardrobe and immediately persists 1–3 resulting outfits.
→ 201, `{ recommendationId, outfits: OutfitDTO[] }`. Rate limited: 30 requests / 15 min / IP.
→ 400 if the wardrobe doesn't have enough items to build an outfit (e.g. no bottoms/dress, or no footwear) — the message is actionable ("add a top and bottom…").

### GET /outfits
Query: `page?` (default 1), `limit?` (default 12, max 50).
→ 200, `{ items: OutfitDTO[], pagination }`.

### GET /outfits/:id
→ 200, the outfit, with its items joined to full `ClothingItemDTO`s (color, image, AI metadata, etc. — never duplicated onto the outfit itself).

### DELETE /outfits/:id
→ 200, `{ data: null }`. Deletes the outfit and its item links (`OutfitItem` rows cascade); the underlying `ClothingItem`s are untouched.

### POST /outfits/:id/feedback
Body: `{ action: "LIKE"|"DISLIKE"|"SAVED"|"WORN" }`. Records a feedback event and feeds the recommendation engine and Style DNA analyzer for future generations — see docs/ARCHITECTURE.md. Append-only: repeated or conflicting actions on the same outfit are all valid (e.g. WORN multiple times, or LIKE followed later by DISLIKE).
→ 200, the outfit with an updated `feedback` summary (`latestReaction`, `saved`, `wornCount`).

Each `OutfitDTO` includes `reasoning` (why these items combine) and `styleExplanation` (the aesthetic read), plus `confidence` (0–1) and a `feedback` summary. This is generated by a rule-based engine reasoning over each item's AI-analyzed attributes, the user's Style DNA profile (if generated), and their past feedback — see docs/ARCHITECTURE.md.

## Style profile (protected — requires `Authorization: Bearer <accessToken>`)

### POST /style-profile/generate
Recomputes the user's Style DNA from their wardrobe, outfit history, and feedback. Explicit action, not automatic — see docs/ARCHITECTURE.md. Rate limited: 20 requests / 15 min / IP.
→ 201, the `StyleProfileDTO`.

### GET /style-profile
→ 200, the cached profile. → 404 if none has been generated yet — the frontend treats this as "show a generate button", not an error state.

### GET /style-profile/preferences
→ 200, the user's explicit `UserFashionPreferenceDTO`, or `null` if never set.

### PATCH /style-profile/preferences
Body (all optional): `{ preferredStyles?, dislikedStyles?, favoriteColors?, occasionPreferences? }`. Upserts — works whether or not preferences exist yet.
→ 200, the updated `UserFashionPreferenceDTO`.

## Health

### GET /health
→ 200, `{ status: "ok", timestamp }`. Unauthenticated, unrate-limited — use for load balancer health checks.

## Error codes

| Code | HTTP | Meaning |
|---|---|---|
| VALIDATION_ERROR | 400 | Request body failed schema validation |
| UNAUTHORIZED | 401 | Missing/invalid/expired token |
| FORBIDDEN | 403 | Authenticated but not permitted |
| NOT_FOUND | 404 | Resource or route doesn't exist |
| CONFLICT | 409 | e.g. email already registered |
| RATE_LIMITED | 429 | Too many requests |
| INTERNAL_ERROR | 500 | Unexpected server error |
